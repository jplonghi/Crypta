# Implementation milestones

The build prompt explicitly requests incremental work and a Phase 1 first deliverable. Phase 1 documentation, the Phase 2 working engine, Phase 3 typed models, and the Phase 4 native app are delivered. [Phase 2 results](PHASE_2_RESULTS.md) record actual evidence and outstanding environment/release checks; [Phase 3 results](PHASE_3_RESULTS.md) cover schema enforcement and model transactions. [Phase 4 results](PHASE_4_RESULTS.md) describe the native app and its verification. [Phase 5 results](PHASE_5_RESULTS.md) cover automatic lock, clipboard ownership, passphrase changes, and keyboard focus. Phase 6 release hardening remains pending.

## Phase 1 — architecture and threat model

Deliverables: requirements analysis, threat model, CryptoKit/libsodium comparison, portable key hierarchy, byte-level v1 proposal, macOS 14 recommendation, package/application structure, risk analysis, and this implementation sequence.

Before release-format freeze, complete reproducible native-artifact provenance, minimum-OS/M1 runtime testing, KDF measurements under memory pressure, a working sanitizer run, and independent review of AAD composition and persistence behavior. Cross-implementation fixtures and local interruption/locking tests now have evidence in the Phase 2 and Phase 3 reports.

## Phase 2 — working cryptographic engine (implemented)

Implemented in `Packages/CryptaCore`. The original acceptance plan follows; see results for what was verified versus unavailable.

First create `Packages/CryptaCore` with only the reviewed libsodium dependency and tests. Do not begin with a SwiftUI shell. Implement a narrow adapter, owned secret buffers, a bounded format codec, an opaque payload create/open round trip, and then encrypted persistence. Use synthetic public payloads until Phase 3 supplies domain types.

| Area | Required acceptance evidence |
| --- | --- |
| Known-answer tests | Pinned upstream Argon2id and XChaCha vectors with provenance and expected bytes, not expectations generated by the code under test. Use vectors matching the exposed one-lane API; do not pretend libsodium's public API accepts all RFC vector parameters. |
| KDF | Identical bytes/salt/parameters reproduce output; changed salt or passphrase changes it; allocation failure is handled; no fallback. |
| Passphrase bytes | Long input, spaces, emoji, composed/decomposed Unicode, embedded NUL, exact confirmation, empty-creation rejection, oversized rejection without truncation. |
| Authentication | Correct unlock; wrong passphrase; modified wrapped key, payload/tag, every header field, and AAD label. Valid-range parameter mutation must fail authentication; invalid-range mutation must fail before KDF. |
| Parsing | Every truncated prefix; boundary lengths; overflow; appended bytes; unknown IDs/version; reserved bytes; malformed JSON; duplicate keys; excessive depth/collections; fuzz corpus. |
| Randomness | Separate creations use fresh ID/key/salt/nonces; save changes payload nonce; rewrap changes salt/wrap nonce. No deterministic RNG in production. Statistical inequality tests alone do not prove randomness. |
| Passphrase change | Current passphrase required; new passphrase works; old fails on updated file; payload bytes unchanged; failed commit preserves original. Demonstrate that an old backup still opens with the old passphrase. |
| Portability | Fresh process without local state opens fixture; independent reference implementation derives/decrypts same fixture; another compatible Mac opens a copied file. |
| Persistence | Mode 0600 staging; no plaintext on disk; short writes; permission denial; disk-full injection; flush/rename failures; interrupted commit yields old/new valid container; encrypted orphan recovery. |
| Concurrency | Two processes using the same local file cannot silently overwrite each other; external replacement/deletion is detected; aliases and symlinks rejected/handled; post-rename ambiguous result reconciled before retry. |
| Memory/lifecycle | Owned buffers zeroed/freed on tested error paths; no plaintext returned on failure; cancellation disposes of results. Do not assert complete Swift memory erasure. |

Run targeted `swift test` suites; archive benchmark hardware/OS/build-mode and maximum memory observations. A bounded parser fuzz target and persistence failure-injection harness belong in this milestone because these are substantive security boundaries.

Exit: tests can create, save, reopen and decrypt a `.crypta` file, with deterministic compatibility fixtures. No real user secrets yet.

## Phase 3 — domain models (implemented)

Implement schema 1 with credentials, API keys/tokens, secure notes, custom fields, categories and tags. Add validation for UUID uniqueness, references, timestamp bounds, limits, and required fields. Verify every field round-trips, including optional expiration, secret-display flags, Unicode, and category membership. Unsupported schemas/types block mutation without data loss. Keep data entirely inside the authenticated encrypted payload.

Exit: typed vault lifecycle and edits work in core tests with no UI dependency.

## Phase 4 — native app (implemented)

Create the Xcode app project, local package integration and `.crypta` document association. Implement welcome, file selection, creation, unlock, sidebar/list/detail, typed entry editor, delete confirmation, explicit encrypted save, and lock. Adopt the transactional editor semantics in the architecture; no plaintext document autosave or state restoration. Meaningful errors distinguish file access/resource problems from the shared authentication failure message.

Exit: a person can perform the complete lifecycle offline through the UI. Test with synthetic data and verify that app file writes never contain it in plaintext.

## Phase 5 — lifecycle and usability (implemented)

Add inactivity/sleep/termination handling, clipboard ownership/expiration, current-passphrase verification and rewrap UI, keyboard shortcuts, in-memory search, accessible labels and focus. Test timers with an injected clock; cover copied secrets followed by another app's write, late callbacks after lock, sleep during KDF/save, and a disabled inactivity setting with sleep-lock still active.

Exit: end-to-end UI and state-machine tests verify actual behavior, including failures and unsaved drafts.

## Phase 6 — hardening and release readiness

Review primitives, composition, parser, dependencies, memory ownership, logs, persistence races, sandbox entitlements, and clipboard behavior. Run on the oldest supported OS and an M1. Test a signed/notarized sandboxed build, not only a debugger build. Perform independent review and resolve findings. Publish known limitations, reproducible build/dependency evidence, format fixtures and a private vulnerability-reporting channel before inviting sensitive use.

## MVP boundary

One local vault/session at a time; four entry types; full-payload encryption; create/open/unlock/edit/delete/search/save/lock; passphrase changes; encrypted portable backups; auto-lock; clipboard expiration. No network runtime, cloud sync, accounts, attachments, biometric/Keychain unlocking, password generator, TOTP, export, or sharing. Future platforms may implement the documented format without macOS APIs. Future optional unlocking mechanisms must preserve file-plus-passphrase recovery.
